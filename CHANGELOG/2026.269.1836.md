# 2026.269.1836 — fix(del): inherit the ledger lock in forked nested member teardowns (charly#680)

## Summary

Fix the ledger-lock self-deadlock in forked nested member teardowns
(**opencharly/charly#680**), cure an in-module test-fixture schema drift found while
verifying it, and pick up the sdk fix that makes the R10 bed tear down cleanly.

A top-level `charly deploy del <root>` holds the ledger transaction lock
(`kit.AcquireLedgerLock`) for its whole body — resolve → members-down →
node-del-dispatch — and forks one **peer** `charly deploy del <member>` per
deploy-level member via `deploykit.TearDownMembers`. The forked child re-enters
`DeployDelCmd.Run()` and re-acquired the **same** ledger lock. `flock` is
per-open-file-description, so the child blocked **forever** on the lock its own
ancestor still held:

```
charly: waiting 14m31s for file lock …/charly.yml.ledger.lock
        — held by pid <parent `deploy del <root>`>; giving up after 30m0s
```

This deadlocked any group bed whose root is an **external-in-place** substrate
(`kindcluster`) with a deploy-level member. `check-k8s-deploy` avoided it only
because its root is a **VM** (`vm destroy` takes no ledger lock).

## The fix — lock INHERITANCE

The parent del marks the ctx it hands to `deploykit.TearDownMembers` with
`CHARLY_LEDGER_LOCK_HELD`; `proc.RunCharlySubcommandCtx` merges the ctx RunEnv
into the forked child's environment, so the child sees the marker and **joins the
ancestor's transaction** instead of re-acquiring the lock.

- `withLedgerLockHeld(ctx)` builds the marker ctx, **merging over** any existing
  RunEnv (never clobbers a bed's `CHARLY_DEPLOY_CONFIG` / `CHARLY_REPO_OVERRIDE`).
- `ledgerLockHeld(ctx)` reads via `spec.RunEnvGet` (ctx RunEnv first, then
  `os.Getenv` for the legacy single-invocation path).
- `acquireLedgerLockForDel(ctx)` returns a **no-op release** on the inherited
  branch, else takes the lock exactly as before.

### 3. The deadlock, reproduced and cured directly

The fix is in the compiled-in `plugin-fleet`. Two charly binaries were built from
this tree — the fixed one and one with the fix removed — and the exact lock
contention the forked nested member hits was exercised. The lock is held
**externally** (`flock`) to simulate the ancestor's transaction; each case runs
`timeout 8 charly deploy del nonexistent-680 --dry-run` — a **dry-run of a
nonexistent name, which mutates NOTHING**:

```
[A NEW +marker] rc=1    (124 = blocked on the ledger lock; other = proceeded)
[B OLD +marker] rc=124
[C NEW no-marker] rc=124
[D OLD no-marker] rc=124
```

| Case | Binary | `CHARLY_LEDGER_LOCK_HELD` | rc | Meaning |
|---|---|---|---|---|
| **A** | **fixed** | `1` | **1 (proceeded)** | the forked nested del **joins** the ancestor's transaction — the fix |
| **B** | pre-fix | `1` | 124 (blocked) | the old code **ignores** the marker → the deadlock |
| C | fixed | unset | 124 (blocked) | a **top-level** del still takes the lock (correct — only nested children inherit) |
| D | pre-fix | unset | 124 (blocked) | baseline |

### 4. The cured fixture drift (R2 — no "pre-existing" parking)
