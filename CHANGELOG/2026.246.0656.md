# 2026.246.0656 — feat(fleet): source-less VM provisioning — from-box vm:

## Summary

Add the VM path of `charly fleet from-box` (cutover task 5): `charly fleet from-box vm:<ref> [name]` provisions a VM from a VM box image in an existing project (a charly.yml must be present — the entity is appended to it). It reads the box image's `ai.opencharly.vm.box` metadata (`deploykit.VmCapabilitiesFromLabels`), extracts the disk layer from the box image (podman save to a temp archive, then a two-hop tar extract through the layer blob), writes a `kind: vm` entity (`source.kind: imported`) into the project's charly.yml, and prints the deploy command (`charly fleet add vm:<name>`). The box image is the source; from-box vm: turns it into a runnable VM entity.

- `parseVmBoxRef`: strips the `vm:` prefix, derives the deploy name
- `vmBoxMetadataToEntity`: metadata → imported-entity mapping (ssh user, firmware)
- `extractVmBoxDisk`: streamed disk-layer extraction
- `writeVmBoxEntity`: yaml.v3 Node API append (comment + key-order preserving)
- `FleetFromBoxCmd.Run` branches on the `vm:` ref prefix
- sdk pin bumped to v0.2026246.640 (VmCapabilitiesFromLabels)

The project's charly.yml gained the entity (source.kind: imported, disk_path, ssh user arch, firmware bios) alongside the `disposable: true` deploy node; the disk was extracted from the box image's layer (12-byte fixture verified at the state-dir path). The disk-extraction fix (two-hop through the layer blob — `podman save` produces an outer tar with nested layer blobs) was RCA'd and fixed in-tree during the proof. The full deploy chain (fleet add vm: + boot) is the cutover's task-9 bed (check-vm-clone), which runs the same flow on a real box image.
