# 2026.309.2138 — fix(deploy): carry the authored security block into the persisted deploy node

## Summary

`charly deploy add` persisted a deploy node's per-host entry without its authored `security:` block. The entry's security came only from the image labels plus auto-detected devices, so an authored `cap_add` never reached `charly config`'s `MergeDeployOntoMetadata` step and the emitted quadlet had no `AddCapability=` line. The container then ran with a narrower boundary than its tree declares — the measured symptom in opencharly/pod-crabbox-k3s#6, where `ip link add k3s0 type dummy` failed with `RTNETLINK answers: Operation not permitted`.

The fix seeds the authored block into the per-host entry after a successful `deploy add` dispatch, at the same position and through the same locked cycle as the existing selector persist. It MERGES into any existing block instead of replacing it: list fields (`cap_add`, `devices`, `security_opt`, `group_add`, `mount`) are unioned with `deploykit.AppendUnique`, so a device detection already recorded is never emitted twice; an authored scalar or `privileged: true` wins; a field the tree leaves unset keeps the existing value. `charly config` then runs its unchanged path: `MergeDeployOntoMetadata` folds the entry onto the image metadata and `AppendUnique` adds the detected devices. A node with no `security:` is a no-op, so the detection-only path is byte-identical; a first-ever image-bearing pod entry is seeded so the documented `deploy add` then `charly config` sequence works. Dotted in-substrate child paths and host-rooted / external in-place nodes are skipped, mirroring `deploykit.PersistBedDeployOverrides`' own guards.

The change is four files:

- `candy/plugin-fleet/deploy_node_security.go` — new: the merge and the seeded persist.
- `candy/plugin-fleet/walk.go` — one call after a successful dispatch.
- `candy/plugin-fleet/deploy_node_security_test.go` — new: the regression tests.
- `candy/plugin-fleet/bed_persist_writer_test.go` — the test-scoped node decoder learns the `security:` block the tests assert.

Closes #42.

## Change classification

Bug fix, additive, no contract change. `charly deploy add` now persists a deploy node's authored `security:` block into the per-host overlay entry, merged with any existing block, so `charly config`'s existing `MergeDeployOntoMetadata` step emits the declared capabilities, devices, and security options into the quadlet. A node with no `security:` keeps the previous behaviour exactly; dotted in-substrate child paths and host-rooted / external in-place nodes are skipped. No schema, wire type, CLI flag, or config format changed.

**Breaking change + rollback:** none — the change only ADDS a persisted field that every binary built from `main` already understands (`MergeDeployOntoMetadata` has merged `overlay.Security` field-by-field since before this branch), and no existing entry is rewritten except to union the authored block into it. Rollback is a revert of the squash commit; entries already written remain valid because they only carry the values the tree itself declares.
