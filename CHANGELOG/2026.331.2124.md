# 2026.331.2124 — fix(deploy): an imported entity's short image: resolves in its own namespace

## Summary

Part of opencharly/opencharly#1316 — the issue stays OPEN: this PR lands the root fix, and the follow-up below (a `charly` release carrying this module, then the imported bed run from the umbrella root) completes it.

A deploy that arrives through an **import namespace** is addressed as `ns.name` (the project
projection) or `ns/name` (the deploy key), but the `image:` it **authors** is a short name for a box
inside its OWN namespace. The resolved-project envelope keys a namespaced box by fullkey (`ns.name`),
so a bare leaf that lives only in a namespace is absent under its bare key — and **both** resolution
sites fail:

```
$ charly deploy add kde-vnc-cdp.check-kde-vnc-cdp-pod --dry-run
charly: error: command "deploy": resolving ref "kde-vnc-cdp" for target "pod":
  ResolveDeployRef: "kde-vnc-cdp" not found as a box or candy in the resolved-project envelope

plugin-deploy-pod prepare-venue: overlay build: resolving "kde-vnc-cdp" via charly.yml: not found
```

**Fixing one alone only moves the failure.** The CLI path dies in `compileNodePlans` before any
lifecycle dispatch runs; a check bed dispatches straight to prepare-venue and dies there. So the rule
is applied ONCE, as one helper used at both sites:

```
qualifyEntityImageRef(rp, entityPath, ref)   // entity_ref.go
```

- `dispatch.go` / `walk.go` — the compile path, and only when the ref came from the node's authored
  `image:` (a user-supplied positional ref is the operator's own spelling and is never rewritten).
- `prepare_venue_extras.go` / `deploy_target.go` — the dispatch a check bed takes, where the envelope
  is fetched only when a node carries an image.

**The qualification is proved by EXISTENCE, never by guessing at the path.** A dotted deploy path is
ambiguous — `ns.name` is a namespace, but `root.child` is a NESTED CHILD (tree position). So a path
head is only treated as a namespace when `head.ref` is a real box in the envelope. A ref that resolves
as written, a full OCI ref, a remote `@github` ref, a local path and an already-qualified name are all
returned untouched.

**No stored shape changes.** The schema keeps the short name the submodule authors, so the same
`charly.yml` is still a standalone project. The alternative — stamping the node at load — would change
what every consumer sees and needs a DESIGN amendment first; it was rejected before any spike.

## How tested

### Spike (R12) — the round, before the fix was kept

Both runs are the same command, from the umbrella's fresh worktree
(`.worktrees/pin-kde-1810/opencharly`), against the imported bed `kde-vnc-cdp.check-kde-vnc-cdp-pod`:

```
# BEFORE — the clone's stock binary
$ charly deploy add kde-vnc-cdp.check-kde-vnc-cdp-pod --dry-run
charly: error: command "deploy": resolving ref "kde-vnc-cdp" for target "pod":
  ResolveDeployRef: "kde-vnc-cdp" not found as a box or candy in the resolved-project envelope

# AFTER — charly rebuilt with this plugin linked in (a spike-only `replace`, never pushed)
$ charly deploy add kde-vnc-cdp.check-kde-vnc-cdp-pod --dry-run
Plan: candy=chrome image=kde-vnc-cdp distro=cachyos steps=4
Plan: candy=nodejs image=kde-vnc-cdp distro=cachyos steps=3
Plan: candy=plugin-cdp image=kde-vnc-cdp distro=cachyos steps=1
…
EXIT=0

# AFTER — the real prepare-venue path, the one a check bed takes
$ charly deploy add kde-vnc-cdp.check-kde-vnc-cdp-pod
Overlay image ready: kde-vnc-cdp_check-kde-vnc-cdp-pod-overlay:916ef71488d8
EXIT=0
```

The spike's overlay image was then removed again with `charly clean --invalidate
'kde-vnc-cdp_check-kde-vnc-cdp-pod-overlay*'`; nothing was left running.

Candidates that were **not** implemented, each rejected on evidence rather than taste:

- *qualify only in `prepareVenueExtras`* — cannot work: the CLI path fails before any lifecycle
  dispatch is reached (the BEFORE run above is that proof).
- *stamp the node at load* — changes an authored shape across every consumer, needs a DESIGN amendment
  and a `spec` release before a spike could be honest.

### Unit coverage

```
$ go test ./...   (in candy/plugin-fleet)
ok  github.com/opencharly/plugin-fleet/candy/plugin-fleet

$ go vet ./...     (clean)
$ gofmt -l .       (no output)
```

`entity_ref_test.go` is the coverage that fails without the change: eleven rows, each a rule — the
measured defect, the slash spelling, a root box untouched, a ref that resolves as written, a nested
child path that must NOT be read as a namespace, an absent box, a full OCI ref, a remote ref, a local
path, an already-qualified name, and no envelope. Plus the prepare-venue half, which is the path a check
bed takes.

**What R10 requires here, and what this round is.** This repo has no per-repo bed; the change-class
gate for a Go change in `candy/plugin-fleet` is `go test ./...` + `go vet` + the changed path executed
LIVE. That is exactly what the round above is: the real command, on a real project, with the changed
path running (`EXIT=0`, **zero warnings** in the run log), against a target explicitly marked
`disposable: true` (`kde-vnc-cdp.check-kde-vnc-cdp-pod`, `lifecycle: dev`) — the deploy built and then
dropped its overlay, and the image it left was removed with `charly clean --invalidate`.

What this round does NOT prove: the same behaviour through a RELEASED binary. The deploy command is
compiled in, so that needs a `charly` release carrying this module version — a follow-up tracked on
opencharly/opencharly#1316, which this PR deliberately leaves OPEN.
