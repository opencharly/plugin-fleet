# 2026.281.0744 — test(fleet): require CHARLY_BIN for the live loader tests, never a PATH guess (#29)

Agent: `retention` · session `task-12` — cluster **C10a** of `plan/issue-ledger-2026-10-07.md`

## Summary

The two live loader tests resolved the charly binary they drive with a **silent
`exec.LookPath("charly")` fallback** — ANY binary on `PATH`, whatever its vintage. So the verdict of a
live test depended on the *host's* package rather than on the tree under test, and the version skew
came out shaped like a defect in `writeVmBoxEntity`: green on a host with no `charly` on `PATH`, red on
a host with an old packaged one (`opencharly/plugin-fleet#29`). This change makes the decision a
**tested, pure function** and never guesses:

- **`selectCharlyBinary(envBin, ambientPath)`** (new, pure): `CHARLY_BIN` set → that binary verbatim;
  unset → no binary, with a skip reason that **names the ambient binary it refused** and why.
- **`charlyForTree(t)`** (replaces `requireCharlyCanLoad`): `CHARLY_BIN` unset is a visible SKIP; a
  named binary that cannot load a **canonical `vm:` config of this tree's own shape** FAILS LOUDLY —
  `VERSION SKEW in the named binary, NOT a code defect` — with that binary's `version` output. The
  assertion failure message now carries `CHARLY_BIN` + its version too, so a boundary failure always
  says which binary produced it.
- **The positive control is now a HAND-AUTHORED config of the asserted shape** (`vmBoxControlConfig`)
  instead of an empty file. An empty config is loadable by every vintage of charly, which is exactly
  why the old probe could not separate "this binary cannot witness this ear's shape" from "the writer
  emitted something broken". The control never passes through `writeVmBoxEntity`, so a real writer
  regression still fails the real assertion — the property the old docstring claimed and did not have.

### The live tests are opt-in, and this repo opts nothing in

Review finding 2 asked for the workflow file + line that sets `CHARLY_BIN`, or a CI log showing the
live arm executing. Neither exists, and the honest repair is to correct the CLAIM rather than cite a
fiction: `ls .github/workflows/` is `tag-on-merge.yml` alone, so **no job here builds a charly or sets
CHARLY_BIN** and the live loader tests skip — visibly, naming the binary they refused — wherever it is
unset, CI included. The docstring said otherwise ("CI's candy job builds a binary and sets
CHARLY_BIN"); that sentence was false for this repo and is replaced by the truth, and the README now
states that the tests are opt-in and carries the command that runs them:

```
$ CHARLY_BIN=<charly-checkout>/bin/charly go test ./...   # 3.24s: the live arms execute
$ go test ./...                                           # 0.44s: the live arms SKIP, and say why
```

Adding a per-repo candy gate to set it is a retired org pattern (per-repo candy gates were removed
org-wide), so this PR does not take that decision; it makes the opt-in explicit instead. The pre-fix
behaviour was strictly worse: the tests silently graded whatever `charly` the HOST had on `PATH`,
which is the defect this PR exists to fix.
