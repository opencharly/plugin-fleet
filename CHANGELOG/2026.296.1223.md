# 2026.296.1223 — feat(deploy): add per-deploy selector flags and persist them on the entry

## Summary

Adds `--engine`, `--backend`, `--namespace` and `--rootful` to `charly deploy add` — the deploy-entity level of the W3.1 precedence chain (`flag > deploy entity > env > settings file > built-in default`), which had no CLI source. The resolver could read a level nothing could write.

- **Validation is schema-owned.** `--engine` goes through `deploykit.ResolvePodEngine`, `--backend` through `deploykit.ResolveVmBackend`, `--rootful` against `spec.RootfulModes`, `--namespace` as a non-empty name. There is no word list in this repo.
- **The candy constraint stays the resolver's decision.** `ResolvePodEngine` receives `Selection{Engine, CandyEngine}`; a composed candy whose `engine:` disagrees is an `engine constraint conflict` error, never an override. This plugin's resolved-project envelope does not carry a candy's `engine:` field (`spec.CandyView` / `spec.CandyModel` have none), so the production call passes the constraint empty and the existing compile-time loader validation remains the enforcement; the wiring and its conflict arm are pinned by test.
- **The flags land on the entity and persist.** They apply to the node shipped to the substrate (flag overrides the authored value) and, after a successful dispatch, are patched onto the top-level deploy entry through the existing locked read-modify-write cycle (`mutateDeployConfig`). Only an entry the substrate created is patched — a fabricated pod entry without `image:` would fail the next load. Nested (dotted) children live inside their parent's entry and are never patched as a top-level one.
- **Flags are refused on the wrong substrate** using the schema's canonical selector table (`pod`: engine/namespace/rootful; `vm`: backend). A `vm:` ref-based deploy is judged as `vm`, because `ClassifyNodeTarget` has no node there and falls back to `pod`.
- **Docs:** the in-repo `deploy` skill lists the four flags and the chain.
- **Pins:** spec `v0.2026276.1103` → `v0.2026296.1036`, sdk `v0.2026276.48` → `v0.2026296.1058`.

No schema field was needed: `spec/schema/deploy.cue` already declares all four fields, and this plugin's schema documents the command contract only (no `#*Input`), so there is no `cue-gen` artifact for this surface.
