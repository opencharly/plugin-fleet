# 2026.323.2140 — docs(deploy): the security posture is captured at deploy add — and a CDI pod cannot use keep-id

## Summary

`/charly-core:deploy` gains the two facts about a deployment's SECURITY POSTURE that this cutover had to
learn the hard way (`opencharly/opencharly#1174`, `plugin-deploy-pod#81`). Both are stated once, in the
quadlet/`PodmanArgs` section where an author looks when a posture is wrong.

Head: `cdded8b` · 1 file, +32

**1. The posture is CAPTURED at `deploy add`; an entity edit does not move a stored deploy.** `charly
deploy add` resolves the entity (image + candy + `add_candy:` overlay) into the STORED deploy and writes
the quadlet from that; `charly config` afterwards regenerates the unit from the stored deploy, not from
the manifest. So changing `security_opt`, `privileged`, `cap_add`, `devices` or a volume in the
entity/candy leaves an existing deployment carrying its OLD posture until you `deploy add` again (or
`update`, which re-resolves for the update it performs).

*Measured:* the GPU pod's unit carried `UserNS=host`, `User=0:0`,
`PodmanArgs=--security-opt no-new-privileges`, `AddDevice=nvidia.com/gpu=all` and an env-target `Secret=`
— all captured at `deploy add` — and a reviewer's correct objection was that the manifest claimed a
security setting the unit did not carry, because the deploy predated the edit. The skill now also carries
the cheap check that answers the question at the UNIT (`grep -E '^(User|UserNS|AddDevice|PodmanArgs|
Secret|Volume)=' ~/.config/containers/systemd/charly-<name>.container`), because prose about a manifest
cannot answer what a running unit does.

**2. A pod that injects a CDI device cannot use `--userns=keep-id`.** The workload runs as container root
under `userns=host`, which IS the invoking host user in a rootless pod (`rootless=true`, nothing
privileged on the host, files land owned by you); the mapping that would protect a bind mount is exactly
the one that makes the CDI mount fail with `mount_setattr … EPERM`. The skill states the consequence and
points at `/charly-cdi:cdi` for the mechanism, the measured matrix and the two legal shapes, then names
the two things that follow:

- `plugin-deploy-pod` DERIVES the user-namespace decision from the resolved deploy (a CDI device present
  ⇒ `userns=host` + container root), so a pod inherits the right shape without declaring it — but a hand
  `podman run` or a new emitter must apply the same rule;
- the workload then needs **no capability at all** (`--cap-drop ALL` measured green), and `#Security`
  cannot yet express `cap_drop` (`opencharly/spec#398`), so a pod declares
  `security_opt: [no-new-privileges]` and cannot state the rest.
