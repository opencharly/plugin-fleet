# 2026.276.1113 — feat(deploy): ship the del target's ancestor chain so the teardown keeps its venue — charly#765

## Summary

**Leg 2 of 3 of the producer chain that fixes `opencharly/charly#765`.** Leg 1 (the wire) merged as **opencharly/spec#190**, released `v0.2026276.1103`; this PR consumes it.

`charly deploy del <root>.<member>` shipped the target node but **no ancestor context**, so the host could not rebuild the `parentExec` chain the `add` half used and the teardown replayed the member's reversible ops (a `package:` list's `pacman -R`) **on the operator's workstation** while its `add` had landed correctly in the guest.

This leg ships the missing DATA: the del dispatch now carries the target's **ROOT-FIRST ancestor path/node lists**.

| file | |
|---|---|
| `candy/plugin-fleet/del_resolve.go` | `walkDeployNodePath` — the ONE dotted-path walk (R3: one resolution, two consumers). `resolveDeployNodeByPath` takes the leaf; `delAncestorChain` takes the whole chain; `delDispatchRequest` is the pure request builder |
| `candy/plugin-fleet/walk.go` | `DeployDelCmd.Run` ships `delDispatchRequest(tree, node, c)` — the request literal it used to inline |
| `candy/plugin-fleet/del_resolve_ancestors_test.go` | NEW — the R10 gate for the chain's shape, its empty cases, **and the wire shape it rides** |
| `candy/plugin-fleet/go.mod` / `go.sum` | spec `v0.2026273.203` → `v0.2026276.1103` |

**The chain EXCLUDES the target and is ROOT-FIRST**, because `spec.ReconstructParentExec` pairs the two lists by index and walks root-first; including the target would derive the target's own executor, one hop too deep. It is **EMPTY** for a top-level or synthetic target (`host`, a bare name, a `vm:` address with no tree entry, a ref-based pod artifact) — a requirement, not a fallback: the host then leaves `RootExecutorForDeployNode` in place and behaves exactly as before this chain existed. `TestDelAncestorChain_NoAncestorsKeepThePreviousBehaviour` pins all six of those cases.

**`vm:` is stripped once, in the walk, not twice.** The address prefix is an addressing hint, never an identity — `delDispatchRequest` strips it, and the chain is resolved against the *stripped* path so both halves agree on the identity.

**No new machinery.** The `add` walk has threaded these same lists to the `resolve-target-add` seam since the K4-C walk port; the del half simply had no equivalent. No executor plumbing is added: nothing live crosses the wire, the host re-derives.

**No `plugin-check` change is needed** — the bed's cleanup step forks a *fresh* `charly deploy del` process, and that fresh process is exactly what now receives the chain.
