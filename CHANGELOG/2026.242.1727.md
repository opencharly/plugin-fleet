# 2026.242.1727 — fix(dispatch): name the missing substrate instead of blaming the ref

## Summary

A `vm:` deploy in a project whose closure lacks `plugin-deploy-vm` fails with:

```
resolving ref "omarchy-vm":
  ResolveDeployRef: "omarchy-vm" not found as a box or candy in the resolved-project envelope
```

**after `charly vm build omarchy-vm` and `charly vm create omarchy-vm` on that same entity
had both just succeeded.** charly plainly knows it is a VM, and the message sends the reader
to fix the one thing that is not wrong — there is no way to make a `kind: vm` entity into a
box.

## The real cause

A target whose workload is entirely `add_candy:` compiles **no primary image**, and reaches
the ref resolver *only* because its substrate was absent from `c.externalSubstrates`:

```go
if target == "local" || c.externalSubstrates[target] {
    base = path          // no ref resolution — the workload is add_candy:
} else {
    ref, refErr := resolveDeployRef(classifyRP, refStr, dir)   // ← lands here
}
```

`pod` and `kubernetes` **do** compile a primary image from their positional ref, so for them
"not found as a box or candy" is the whole truth and is left untouched.

The annotation is keyed on *"this target compiles no primary image"* rather than a hardcoded
substrate list, so a future substrate gets the hint without a code change.

The resolution error is **preserved verbatim and wrapped** — `errors.Is` still finds it, no
evidence is lost, and the target name is added to the outer message.

```

```

Three tests: the cause is named for a non-image target and the original error survives
(including `errors.Is`); `pod`/`kubernetes`/`local`/`""` pass through **untouched**; an
unknown future substrate gets the hint for free.

**Negative control — annotate everything, including pod:**

```
--- FAIL: TestAnnotateMissingSubstrate_LeavesImageBearingTargetsAlone
    target "pod": the error must pass through untouched; got: the "pod" deploy substrate
    is not available in this project …
```

That is the control that matters: the tempting version of this change muddies a genuinely
correct message for the two targets where the ref really is a box.

### The call path is covered — this is the second revision

A first revision tested `annotateMissingSubstrate`'s **logic** only, and removing the call
site left those tests green. I disclosed that; the reviewer correctly rejected it, because
the behaviour this PR ships *is* the annotation being applied where the resolver fails.

The join is now extracted as `resolveRefForTarget` — one function, testable — because the
compile path around it needs a fully resolved project and a live loader a unit test cannot
stand up. Two tests drive it exactly as `compileNodePlans` does: an empty envelope (no boxes,
no candies) and a plain local name, precisely the shape a `vm:` deploy hits when its
substrate is absent.

**Negative control — remove the annotation from the call path:**

```
--- FAIL: TestResolveRefForTarget_AnnotatesOnTheCallPath
    the call-path error must contain "for target vm"; got:
      resolving ref "omarchy-vm": ResolveDeployRef: "omarchy-vm" not found as a box
      or candy in the resolved-project envelope
    the call-path error must contain "plugin-deploy-vm"; got: ...
```

The `pod` case is covered on that same path: it must **not** gain a substrate theory it
cannot have.
