# 2026.332.0004 — fix(deploy): qualify the image the dispatch actually sends, over its own executor

## Summary

Closes the deploy-side half of opencharly/opencharly#1316, in three rounds:

**Round 1–2 (the dispatch's image).** The compile path resolved the authored `image:`, but the path a
**check bed** takes did not: its deploy dispatch carries **no node image**, and the image reaches the
substrate from the compiled plan's `Box` — the bare leaf for an imported entity. `prepareVenueExtras`
now qualifies the image it actually sends, over **this dispatch's executor** (`resolveProjectViaExecutor`)
instead of the CLI-only `cmdExec` global, and a failed resolve is **reported**, never swallowed.

**Round 3 (the resolution ORDER, per DESIGN).** Resolution is now **namespace-only** for an imported
entity — no bare-name fallback:

- `D-LOAD-6` — the scope a reference resolves in is the document it is written in;
- `D-REF-1` — the identity's first segment is a namespace if one with that name exists;
- `D-REF-2` — no search path, no catalog, **no fallback**;
- `D-REF-6` — an imported project resolves its own names, which the importer does not see.

The scope is decided from the identity alone (D-REF-1's existence test), and the ref resolves there
and nowhere else: a ROOT box sharing the leaf **cannot** answer for an imported entity, a missing box
is still qualified so the owning resolver reports it, and a root entity or nested-child path is
untouched.

Round 2 also removed the R2 duplication the reviewer flagged (one `resolvedProjectVia` body).
